## Runtime design and original failure investigation

The original personal profile ran 0.1.0-dev (`89C93CAEF7B1B38978FFB7747392F20E6858F2884CBBD57AA35B47D9F087738F`). An early config disabled enrollment. A later read-only Test04 audit found 161 legacy managed, 93 pending, 94 filled ordinary, 44 ordinary table-backed and 11 empty chests. All 12 examined tower chests were pending at native Locks phase 1. This explains how chests could appear ordinary even when enrollment was enabled. Other independent issues included updates arriving before the client tile, cached states after tile recreation and an initially invalid Quark test fixture.

- Generation events and live tile identity establish provenance. Disk-loaded tiles are excluded. The deferred registration queue respects actual Locks readiness across both halves, so Mods see the original loot during lock generation. Ambiguous and player-created storage stays ordinary.
- Adapters keep native tiles, pairing, table semantics and physical automation buffers. Server-only chunk records hold identities and sources. Cart records use the persistent entity UUID and world MapStorage. The native lock decision precedes the private menu. A scoped first-use transaction lets RLArtifacts roll once.
- Player NBT checkpoints tie private inventory changes and cursor recovery to the same file as a player's vanilla inventory. Separate baselines handle player/chunk save order. Verify durability of the **first** registration independently.
- Viewer-specific state travels on watch/tracking and after access. The renderer adds project-authored geometry over native models. HUD and world rendering have separate acceptance tests. Full architectural rationale and extension contracts are in [developer notes](DEVELOPMENT.md).
