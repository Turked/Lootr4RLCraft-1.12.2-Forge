# RLCraft 2.9.3 qualification

This is a development candidate for Minecraft 1.12.2, Forge 14.23.5.2860 and Java 8. Each result below applies to the environment and artifact identified alongside it. A check against an installed class, a scripted server player and a connected game client exercise different paths.

The November 26 connected-client retry preserved partial Families evidence. Two clients completed the initial and chunk-return capture sweeps. Three clients verified the existing diamond allocation. The saved double Rustic cabinet had only one managed tile and opened a 27-slot menu. Corrected fixture provisioning and the full three-client rendering, travel, reconnect and restart matrix remain unverified. [Desktop continuation checkpoint](DEVELOPMENT_CHECKPOINT.md)

## Evidence from the reported profile

The inspected `RLCraft (1)` profile had `Lootr4RLCraft-0.1.0-dev.jar`, SHA-256 `89C93CAEF7B1B38978FFB7747392F20E6858F2884CBBD57AA35B47D9F087738F`. Its saved config enabled new registration, fixed inventories and indicators. A read-only scan of Test04 found 161 legacy managed chests, 93 ordinary chest tiles carrying a pending registration, 94 filled ordinary chests, 44 ordinary chests with native tables and 11 empty ordinary chests. All 12 chests in the recorded Tower-edit footprint carried pending registrations and Locks phase 1. A player looking at a pending chest could therefore see the original chest. That save establishes the state at save time. It cannot establish what happened during an earlier visit. See the repeatable [world-file reader](tools/audit_saved_chests.py).

The original timing logic could go dormant after one early readiness check. A stationary player's view could also arrive before its tile or miss an update after local tile reconstruction. Existing builds drew only trim and lacked a targeted HUD provider. The current code records generation provenance, wakes pending registrations when watched, sends per-viewer states and renders the marker independently of the native chest renderer. The archive of rendered client tests includes the before/after images and exact JAR hashes. [Client evidence](qa/evidence/client/README.md)

## Reproducing the dedicated run

Use an isolated copy of the [publisher's 2.9.3 server pack](https://www.curseforge.com/minecraft/modpacks/rlcraft/files/4612990). Supply the matching Forge installation and Java 8. The local test uses seed 81327831, a fresh world, command blocks, a loopback listener and synthetic offline identities. It has no network exposure beyond the local machine.

1. Run `.\gradlew.bat build reobfServerProbeJar`. Put the project JAR from `build/libs` and the test-only JAR from `build/qa-server/probe` in the isolated server's `mods`. Confirm their hashes. The requested product consists only of the former JAR.
2. Launch the server, wait for Done, and enter `lootrqa generate` at the server console. The fixture calls the installed Ruins generator for 25 copies of TowerMedium, records all 175 original chest positions, and exercises Forge's chunk-watch subscribers. The test controls placement and records independent pre-allocation inventory evidence.
3. After GENERATED and Locks' delay, run `lootrqa status` and then `lootrqa sample`. Record registration counts **before** interaction, native denials, three-viewer counts, and exceptions. Also run `lootrqa compat` and `lootrqanatural` on the builds that include those probes. Entries with obstructions or native locks require their own assertions.
4. Run `save-all flush`, then `stop`. Restart the same world with the same JAR hashes and run `lootrqa verify`. The probe loads the actors' player files and compares each saved private slot to its expected NBT. A reconnect through the network requires a separate client test.
