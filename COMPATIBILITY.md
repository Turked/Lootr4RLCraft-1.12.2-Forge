# RLCraft 2.9.3 compatibility audit

The reference client is the local CurseForge `RLCraft` instance. Its `manifest.json` reports RLCraft 2.9.3, Minecraft 1.12.2, and Forge 14.23.5.2860. The local mod directory includes additional mods, including `dregora-lootr-workaround-1.0.0.jar`. The audit used the manifest, mod filenames, installed mod class signatures and event wiring, pack configuration, and logs. A clean pack client and matching dedicated server are needed for runtime qualification. [RLCraft 2.9.3 client and server files](https://www.curseforge.com/minecraft/modpacks/rlcraft/files/4612979/additional-files)

The local `logs/latest.log` records a successful launch, an integrated world session, and a normal shutdown. The latest log and six archived logs contained no standalone Lootr or MixinBooter crash trace. The original Lootr publisher lists MixinBooter as a requirement for its 1.12.2 build. This project targets Forge hooks and can use the pack's existing mods as optional integrations. The reported original Lootr launch failure remains undiagnosed for this installation. [Original Lootr requirements](https://www.curseforge.com/minecraft/mc-mods/lootr)

The subsequent `RLCraft (1)` test profile loaded Lootr4RLCraft 0.1.0-dev successfully on both sides of its integrated server. Its saved `registerNewChests=false` setting disabled enrollment. A read-only scan of its `test02` world found 217 filled vanilla chest tiles with no retained loot table, 129 vanilla tiles retaining a table, and 20 empty vanilla chest tiles. Its level data reports the default generator. This confirmed the need to cover prefilled structure chests alongside retained native tables, as well as explicit conversion of existing test chests. The updated adapter provides those paths and native double chests. Actual pack rendering and mod interactions need in-game verification of the updated build.

### RLCraft (1) test03 investigation on November 18, 2026

A read-only scan of `saves/test03` found 2,199 saved chunks and 392 chest tiles. Of these, 233 were managed, including 213 single chests and 20 linked halves forming ten complete double chests. Four additional physical double chests retained ordinary chest tiles. A representative managed double is at `-8034 72 -5366` and `-8033 72 -5366`. The profile had all three automatic registration options enabled and shut down normally after the test.

The tower near the saved player position comes from Ruins' `config/ruins_config/plains/TowerMedium.tml`. The world's `RuinsPositionsFile.txt` records this template at bounds `-8018 80 -5292` through `-8006 125 -5280`. Its 46-layer template uses an embedding distance of 17 and defines exactly seven isolated chest cells. A 180-degree rotation with world origin `-8018 63 -5292` reproduces every saved chest position. The six floor chests are at `x=-8011`, with `(y,z)` values `(67,-5287)`, `(74,-5286)`, `(81,-5287)`, `(88,-5286)`, `(95,-5287)` and `(102,-5286)`. The upper chest is at `-8016 108 -5287`. All seven have managed fixed-content records. Two contain the testing player's saved private inventory. This template's intended layout has seven single chests.

Locks' saved generation marker is phase 2 throughout that tower, and the tower contains no saved lock regions. The whole world contains eight saved lock regions. The earlier adapter emptied a fixed chest's physical inventory before Locks' delayed generation pass inspected it, which could cause Locks' skip-empty rule to suppress those locks. The revised registration timing needs an in-game retest with newly generated containers. Existing tower geometry and lock outcomes were preserved during this audit.

## Interaction and world generation

### Locks 3.0.0

`config/locks.cfg` protects lockables and includes vanilla chests, Quark chest variants, Varied Commodities barrels, Charm barrels, and Rustic barrels and cabinets. The installed release stores lock regions in world and chunk capabilities. It exposes `LocksUtil.locked(World, BlockPos)` for a block position. Leave regions, the lock renderer, key handling and lockpicking under Locks control. Locks’ normal-priority right-click handler can set `useBlock=DENY` and still let an item action continue. An independent GUI route needs to respect the result and check authorization for the whole container, including the connected half of a double chest.

The native lock-generation handler looks for chest blocks with chest tiles and treats a pending loot table as non-empty without generating it. For chests without a pending table it inspects the physical item list and uses the configured always-lock and skip-empty rules. Removing the table or emptying the inventory before Locks examines it changes the chance of a generated lock. Leave the native pending-table signal available for this check. [Locks project and releases](https://www.curseforge.com/minecraft/mc-mods/locks/files/all)

### RLArtifacts 1.1.2 and Mimics

`config/RLArtifacts.cfg` sets a 1% chance for an unopened loot-table chest in the configured dimensions to become a Mimic when opened or broken. Installed RLArtifacts observes block clicks and breaks at `LOW`. Its click handler checks block use permission, server side, player and dimension, and chest obstruction. Both paths require an instance of `BlockChest` and `TileEntityChest` with a pending native loot table. The handler calls the tile’s `fillWithLoot(player)` before rolling the chance. If it wins, the handler cancels the interaction, replaces the chest and spawns the Mimic.

Allow RLArtifacts to make the native first-open decision. A compatible adapter needs to retain the pending table through that event, avoid granting an inventory when the chest becomes a Mimic, and avoid exposing a fresh pending table on later clicks. Test repeated clicks, a break before first open, and the second player’s open with a deterministic test configuration. [RLArtifacts project](https://www.curseforge.com/minecraft/mc-mods/rl-artifacts)

### Luckified

Luckified was absent from the inspected client profile. Retain the opener’s luck in the Forge loot context and preserve table modifications visible through the world’s loot manager. Whether the optional Luckified build recognizes the managed chest and applies further behavior needs an installation-specific audit and a test with that build. [Luckified project](https://www.curseforge.com/minecraft/mc-mods/luckified)

### Carry On, automation, and movement

Carry On `1.12.7.23` can handle a normal-priority right-click when both hands are empty and its server-synchronized carry key is active. Its pickup permission check can post a synthetic Forge `BreakEvent` before it serializes and removes the tile. A later right-click listener may run after the tile has moved. The installed RLMixins `1.2.15` has `CarryOn Ungenerated Chest Patch` enabled. Its protection recognizes chest blocks with a chest tile that still reports a pending loot table. Managed chests also need protection after their first open. A precise early deny can use the version-specific server-side carry-key flag and target managed containers. Verify Carry On placement, both hands, and a custom key binding in the installed version. [Carry On project](https://www.curseforge.com/minecraft/mc-mods/carry-on)

Hoppers and comparators can inspect inventories through Forge item handlers or direct native inventory methods. Clearing contents after another system has already read them can leave loot available twice. Anchoring managed data to an authenticated container identity and preventing private loot from entering the physical inventory are necessary for safe retries, breaks, explosions and replacement. Verify outcomes through both the vanilla and capability paths. Minecraft 1.12.2 has no general transaction between the player inventory file and the chunk save, so crash-recovery tests need to include interruption during item transfer and save.

### Generator provenance and existing worlds

The local pack includes Recurrent Complex `1.4.8.4`, Roguelike Dungeons Fnar Edition `2.4.4`, Doomlike Dungeons `1.14.12`, and Lycanites Mobs `2.0.8.9`. Each generator needs a verified registration point and a test that its containers are registered before another system can materialize or consume loot. Native population emits its post event before Forge invokes registered mod world generators. Native generation can also write across chunk boundaries. Compare loaded tiles before and after a known generation pass to avoid enrolling preexisting storage merely because it has a pending table. Keep ambiguous and pregenerated containers outside automatic eligibility until an adapter can preserve their semantics. [Forge 1.12.x chunk generation patch](https://github.com/MinecraftForge/MinecraftForge/blob/1.12.x/patches/minecraft/net/minecraft/world/chunk/Chunk.java.patch#L230)

Existing-world migration requires a backup and explicit administrator opt-in. Previously opened or emptied containers cannot be accurately reconstructed from empty slots. Verify opt-in selection, one-time migration, unchanged ordinary storage, and recovery from a failed migration before offering bulk conversion. [Official RLCraft releases and changes](https://github.com/RLSquad/RLCraft-Public/releases)
