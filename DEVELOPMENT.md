# Container adapter development

`GenerationDiscovery` records tile construction identities during generator calls. Population scopes, the first and last additional world-generator callbacks, Recurrent Complex events, Ruins template events and Doomlike chest events provide provenance. Completed scopes retain only objects that are still the live tile at their final position. Disk-loaded tiles are subtracted from active scopes. This covers distant placements and same-position replacements without enrolling ordinary storage from cascading chunk loads. A matching position or a loot table by itself never proves that the generator created the tile. Aborted scopes expire at the end of the world tick.

Locks 3.0.0 performs its own generation after chunk tracking and a delay. `DeferredChestRegistration` leaves the original tile and its physical contents intact until the native Locks chunk capability reports completed phase 2 for every half. A small eligibility marker persists the original position, block and canonical NBT fingerprint through chunk and world saves. Only marked, unchanged original tiles can resume. The marker contains no item stacks. Chunk load and watch events schedule attempts, including a deadline after the latest watch, and pending block interactions wait for generation while allowing item actions. A changed original remains ordinary.

`ContainerLoot` handles every new registration through adapters. It preserves original blocks and tile classes. An opaque routing marker identifies a container group and its anchor chunk. `ContainerChunkData` stores private sources and player inventories in a server-side chunk capability. Vanilla chunk packets include tile update tags and omit chunk capabilities, so private records stay off the client. Loaded private data follows chunk lifetime. The older `InstancedChestTile` remains readable for worlds created by earlier development builds.

Adapters resolve the installed container's own pairing rules, capture source NBT and replay native loot generation on a detached instance of the same class. Charm uses its own loot-size algorithm. The detached Charm inventory handler avoids bookshelf callbacks that would update the real world. Slot rules and limits remain in use in the private menu. Inventories with a non-multiple-of-nine size use read-only padding to fit the native chest menu.

Registration prepares private records before changing physical contents, clears and verifies every original slot, then installs the public marker. A failed registration restores original NBT and removes the uncommitted private record. The native physical inventory remains an automation buffer independent of player loot. Player menu changes never pass through it.

The first native chest interaction temporarily restores the original pending-table flag so RLArtifacts can make its normal Mimic decision. A scoped transaction preserves any physical automation items. If the chest survives, its generated first roll is saved for that opener and the buffer is restored. If it becomes a Mimic, native drops occur once and a surviving paired part retains its record. Anchor removal migrates surviving data to the surviving chunk. Unfinished interactions are completed at the end of the tick.

`ChestLootData` stores a schema version, identity and each player's slots. Table records from older builds remain supported. Generated records take an adapter callback for the first roll, while later opens read the saved inventory. Use one data object per loaded record and perform all changes on the server thread. Update the private record on every committed inventory change and mark its host chunk dirty.

Fixed records store an explicit item template in the same schema. They preserve item NBT and slot layout for prefilled generation and administrator-selected `convert-fixed`. Reading earlier table-only records remains supported. Each player receives independent ItemStack instances and later changes persist separately.

PlayerCheckpoints keeps the last private inventory in the same persistent player NBT as vanilla inventory, keyed by the independent loot-record UUID. Server-side storage retains the mirror and an immutable initial or pre-upgrade inventory for recovery when the player file predates its first checkpoint. The compactIdenticalCheckpoints option stores one item list when baseline and mirror match. Direct drops from a private menu are refused. Closing returns a carried stack to the player, and a full inventory leaves a recoverable overflow in player data. Test player-file-newer and chunk-file-newer cut points with real item metadata, including the first open, cursor pickup and reconnection.

CartRecords uses the shared world MapStorage and the entity UUID. Carts keep their installed entity class and a separate physical automation buffer. Tracking packets include the dimension, numeric entity ID, entity UUID and the recipient’s marker state. Retain saved records if the entity unexpectedly disappears. Treat unknown data as unavailable on errors.

Before enabling another adapter, establish its generation provenance, ownership, physical identity and loot behavior. Test native authorization, automation, removal, and the adapter's full save and unload lifecycle. Paired storage requires stable whole-container identity and checks both halves. Entity storage requires a stable entity UUID. Pregenerated contents need a policy grounded in the generator's original semantics. Refer to [the installed container audit](COMPATIBILITY.md) for classes, behavior, and open issues.

Only the current player's marker state goes to the client. Send the initial snapshot on chunk watch and refresh the player's marker after a successful open. The client drops markers on chunk and world unload. Keep private NBT out of update tags and out of shared packets when adding an adapter.

The inventory title is the literal string `lootr`. The resource pack declares format 3 for Minecraft 1.12.2 so locale lookup uses the packaged `en_us.lang` path. Tests read real pack metadata and language resources instead of relying solely on a manually injected language map.
